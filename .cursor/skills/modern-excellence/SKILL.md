# Modern Excellence

**What** — turn the best relevant capabilities available today into a working improvement that makes this repository more valuable over time.
**Use when** — asked to modernize through implementation, unlock new capability, or make ambitious long-term progress in any repo. **Skip when** — the user wants only research or has already specified a narrow change.
**Run** — the target repo's relevant checks and actual workflow · **Read** — repo instructions, implementation, recent work, and current primary sources · **Write** — working changes and verification evidence in the target repo's existing work record
**First move** — inspect the target repository and trace a real user or machine workflow to understand what it delivers and what limits it.

## Mission

What could this system do substantially better now, given what has become possible, and what should we build to realize that?

Execute when invoked. Return a demonstrated improvement, not a rewritten prompt, a menu of ideas, or a plan awaiting routine confirmation. Be ambitious about the outcome and exacting about the implementation. An outcome may require several connected changes; do not shrink it to a cosmetic patch just because that is easier to finish.

## Understand, then invent

Read the target's instructions, architecture, important code paths, recent changes, and relevant open work. Treat its name and old documentation as hypotheses to verify. Establish what runs, who or what uses it, and where value is lost or capability is missing. Check previous work before repeating a modernization pass.

Explore beyond the backlog. Research current official documentation, engineering posts, primary repositories, and papers when they could change what you build. OpenAI, Anthropic, and other frontier builders are useful starting points, not a mandatory vendor list or an architecture to imitate. Include domain-specific advances when they matter more than agent infrastructure.

Translate a promising capability into a concrete opportunity here: what existing limitation changes, which implementation would use it, and how you would demonstrate the gain. Verify claims about current capabilities from sources read in this run. If sources are unavailable, say so; use local evidence for work that remains justified without asserting frontier superiority.

## Choose with taste

Compare the strongest plausible directions briefly, then commit to the one with the clearest substantial benefit. Favor new useful capability, better real results, less recurring work, or a foundation that demonstrably accelerates the next workflow. Consider ongoing cost and maintenance alongside upside, without invented ROI scores.

Apply the useful Jobs principles: question inherited assumptions, own the complete experience, simplify difficult things for the user, and hold the finished result to a high standard. A new dependency can be the right answer. So can deleting an abstraction or using a powerful API directly. Modernity earns its place through the result, not its release date.

State the intended gain and a practical before/after check, then implement. Use judgment about scope. Finish the connected path to the outcome rather than accumulating unrelated improvements. Honor existing authority and access boundaries; this skill does not authorize spending, production changes, messages, or live execution beyond the user's request.

## Build and prove

Use available tools, integrations, and independent agents wherever they improve speed, discovery, or quality. Give parallel work clear ownership; use an independent reviewer or realistic behavioral evaluation for substantial changes. If delegation is unavailable, continue with an explicit verification pass. Choose available models appropriate to the work; do not hard-code a model that will age out.

Exercise the behavior the change is meant to improve. Compare with the baseline using a real workflow, representative fixture, benchmark, or held-out evaluation as appropriate. Test consequential failure paths. Distinguish local, mocked, and live evidence. Passing lint or configuration checks alone does not establish user value.

Follow through on failures within scope. When an external dependency blocks completion, finish useful independent work and identify the exact missing input or authority. If investigation establishes that no proposed change is worthwhile, explain that with evidence rather than manufacturing churn.

Preserve the result, relevant source links, and remaining limitations in the target's existing PR, commit, or work record. Reuse that record on the next invocation; do not write target-specific state into the shared installed skill package.

Finish with what became possible or better, how it was verified, and any material remaining limitation. Do not promise financial returns from engineering progress.
